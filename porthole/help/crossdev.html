Building for other computers

The crossdev plugin builds a whole Gentoo system for another computer on this one: another architecture (a Nintendo Switch, a Raspberry Pi, an arm64 server) or the same one. Packages are cross-compiled with a toolchain made for the other computer; what won't cross-compile is built inside the system under emulation (qemu), still compiling on this computer over distcc. The finished system is a folder you can write to a disk or export, and Porthole running on it takes over from there.

Getting started

Switch the plugin on in Settings, Plugins. Its windows are then in the Active Plugins menu:

Ready to build for another computer?
Checks what building needs on this computer: crossdev, qemu's user-mode emulator for the other architecture, the kernel's support for running other architectures' programs (binfmt_misc), distcc, and the kernel's overlay filesystem (overlayfs, see below). Anything missing has a button that adds it to the install queue or sets it up; Set up everything missing does them all.
Systems for other computers…
The systems Porthole has made, and everything you do with them.

Systems

New system…
A name, a profile (the board's repository usually has one: add it with Add a repository… if it isn't listed) and the repositories it uses. Porthole makes its folder and settings; nothing is built yet.
Keeps packages (a column in the list)
Ticked, a binary package of everything built for the system is kept (FEATURES=buildpkg in its make.conf), in its own folder (see Where things are). Builds install from them instead of compiling again, Start over keeps them, and the computer the system is for can install from them or they can be hosted for it.
Settings…
What the system is: its settings, package list and first-boot setup.
Build its toolchain…
The cross compiler (binutils, gcc, the kernel headers and C library) the system's profile asks for. Systems wanting the same versions share one; Toolchains… lists them.
Build the system…
Works the whole build out first and shows it before anything is built: see Building.
Make an image…
Makes the built system into something to boot on its computer, such as a live SD card: see Making an image.
Open a shell in it…
A root terminal inside the system (under qemu when it is for another architecture), for looking around or fixing something by hand. Builds of it don't start while the shell is open.
Start over…
Removes everything installed in it, keeping its settings, package list, first-boot setup and binary packages: the next build installs what is already packaged instead of compiling it again.
Delete…
Deletes everything built for it on this computer: its folder (with its settings) and its binary packages. A computer it is installed on keeps what it has.

A system's settings

The profile's values are only a start: look through each tab and set what this system should be. Overview lists what still needs looking at. Changes show in a bar at the top; Save asks for the administrator password and writes them into the system's own make.conf (in a block of Porthole's; your own lines are kept).

Overview
The profile (Change profile…) and a checklist for before building.
Compiler
The CPU it is built for (always named: never native, which would mean this computer's) and parallel builds (MAKEOPTS, from the computer it is for).
USE flags
The system's global USE flags, searchable. The search finds every flag a package in the system's repositories has, including a board repository's own flags that nothing describes (shown with the package that uses them). A flag only one package uses is better set for that package, on the Packages tab.
Hardware
The computer it is for: CPU threads and memory, video cards, input devices, CPU features and languages. Nothing is found out here (this isn't that computer): choose them.
Build options
Stable or testing packages, FEATURES and accepted licences.
Packages
What the system installs (its @world): start from a ready-made list, search for packages, and set USE flags per package.
First boot
What it needs to boot, let you log in and get online: see below.
Files
The system's own Portage files, for anything the other tabs don't cover.

First boot

Settings no package installs: the computer name, time zone, language, keyboard, the root password, your account (and whether it may use sudo), the network at boot, Wi-Fi, and logging in over the network (sshd). Passwords are stored only as hashes, readable by root alone. The packages these need are added to what the system installs. Everything here is written into the system at the end of each build, after its packages, so it doesn't collide with the files they install. Where each comes from shows, for each, whether this setup or one of the system's packages sets it.

Started at boot

Which services the system starts, and when. On OpenRC each service starts in a runlevel:

  • sysinit: the first things: device nodes, /proc and /sys, udev.
  • boot: bringing the system up: disks checked and mounted, clock, hostname, keyboard, elogind.
  • default: what runs once it is up: the system logger, cron, the network, sshd, dbus, the desktop.
  • shutdown: on the way down.

On systemd a service is either started at boot or not (it is enabled for the target its unit asks for, as systemctl enable does).

The list shows every service the built system starts and who set it: set by its package (most packages put theirs in place as they install), Porthole (what the other first-boot choices start: the network, sshd, the desktop with dbus and elogind) or set here. Above them come suggestions: services the system has but doesn't start yet, that its packages' install notes say to start (rc-update add … or systemctl enable …), or that every Gentoo system usually runs (a system logger, cron) when one is installed.

  • To change when a service starts, click its Starts column and pick a runlevel, or not started.
  • To add one, type its name under the list (it completes from the system's services), pick when it starts and press Add.
  • Save the first-boot setup keeps your choices. When the system is built already, the services change in it straight away; every later build keeps them so. Before the first build the list is mostly empty: it fills in once packages are installed, and what you add is set at the end of the build.

Take care with sysinit and boot: a system without udev, localmount or root there may not come up.

Building

Build the system… asks portage to work the whole build out first (as you, nothing changes yet) and shows:

  • the packages that go into the system,
  • changes the system's own settings need (USE flags, keywords), made in its package.use and package.accept_keywords files 00-porthole-build,
  • On this computer: build tools that run here while the system's packages build, installed or rebuilt on this computer as in any cross build, and any accounts they add to it (a package that sets file owners by name while it builds needs that account here),
  • changes this computer's settings would need for those tools (often one more Python version), only made when you tick that you allow them, in /etc/portage/package.use/porthole-cross-<name>, removed with the system.

Build it queues the build as a job (see the job window). In order: a check that the build still works out, the kernel headers and C library, the base system (@system), what the first-boot choices need, the system's own list (@world), installing its kernel, removing what nothing needs any more, the first-boot setup, and a health check. A build can be stopped and started again; it picks up where it stopped, installing what is already packaged.

When a package won't cross-compile, the next step builds it inside the system under emulation, then the stage carries on. When emerge stops on a circular dependency, the next step builds the package it suggests with the USE flags it suggests, then again with its usual ones.

A kernel package installs its kernel when it is merged: installkernel writes /boot and its hooks make the initramfs and the board's boot files. Run from this computer, that would be this computer's installkernel, so during the build the kernel is only noted; the Install the kernel step then installs it inside the system, through the emulator (emerge --config, the package's own way of doing it again), with the system's own installkernel, hooks and dracut. This covers kernel packages built with Gentoo's dist-kernel eclasses (a board's prebuilt kernel package, gentoo-kernel); a kernel you build by hand from sources inside the system is installed the usual way there. The step ends by listing what is in the system's /boot.

If installing a kernel fails, the step says so and the kernel stays on the list: the next build tries again. To do it by hand, Open a shell in it… and run emerge --config =<the kernel package> (the step doesn't run while a shell is open).

The health check at the end looks for programs built for this computer instead of the system, libraries a program needs that aren't there, perl and Python modules under this computer's names, kernel modules without their index, accounts, and configuration files with a package's new version still waiting (it first settles the ones that need no decision; see Configuration updates). Errors fail the build; warnings are only reported. Run it again any time, as root:

porthole-update-service plugin crossdev health <name>

Each job also writes a command record (<job>.sh next to its log) with every command it ran and why: what building the system by hand would take.

Making an image

What a system is made into to boot depends on its computer, so the system says it: its board's packages install a recipe for each kind of image in /usr/share/porthole/images. Make an image… lists them. Pick one to see what it is, where its files go and whether the system is ready for it. A recipe can need packages built with certain USE flags (a live image needs a kernel that can boot from one, say). Until the system has them, it says what to change in its settings before you build it again.

Making the image is a job (see the job window):

  1. The system is copied out the way it is set up for its computer (repositories copied in, make.profile pointing at them, nothing about building here), into a folder next to the image.
  2. That copy becomes a squashfs, without what is left over from building (/tmp, /var/tmp, downloads), and the copy is deleted again.
  3. The files the computer's bootloader loads (kernel, device tree, boot script, bootloader settings) are copied from the system next to it.
  4. Every file is checked against the largest file the card's filesystem takes (FAT32: 4 GiB).

The result is a folder, card, laid out the way the card should be. Copy everything in it to the card; the recipe says which partition it goes on and how to boot it. Making the image again replaces the folder. The squashfs needs mksquashfs on this computer (sys-fs/squashfs-tools); if it is missing, the window offers to add it to the install queue.

From a terminal, as root:

porthole-update-service plugin crossdev images <name>
porthole-update-service plugin crossdev package <name> <recipe>

Writing a recipe

For a board's maintainer: a recipe is a small file, installed by the package that installs the boot files it uses (so they always match), as /usr/share/porthole/images/<recipe>.conf:

[image]
title = Live SD card
about = What it is, where its files go and how to boot it.
# packages it needs in the system, with the USE flags that matter
needs = sys-kernel/board-kernel[live] sys-boot/board-boot[live]
# the system as a squashfs, at this place in the image (optional)
squashfs = boot/rootfs.squashfs
compression = xz
# the largest a file may be, in bytes (FAT32: 4294967295)
max_file_size = 4294967295

[files]
# place in the image = file in the system (links are followed)
boot/kernel = /boot/vmlinuz
boot/board.dtb = /boot/board.dtb

A flag written -flag in needs must be off. Porthole only runs these generic steps; everything about the board stays in its packages.

This computer stays as it is

A cross build installs into the system's folder, but its packages' install scripts run on this computer, as root. So every emerge into the system runs where this computer's /etc, /usr and /var are behind an overlay only that emerge sees. It reads them as they are; what it writes there goes to a scratch layer, not to them. Only the system's own folder and settings and portage's build, download, binary package, cache and log folders are written for real.

When the emerge ends and the scratch layer is empty (the normal case), nothing happened. When something is in it, a package tried to change this computer (a user added to /etc/passwd, a file in /usr): the step fails, the log lists each file, and a copy of what it wrote is kept in /var/lib/porthole/sandbox/<job>/ for you to look at. Nothing is copied back.

The build tools this computer needs are installed before each emerge that needs them, in an emerge of their own, and only those the build's plan listed when you agreed to it (and those the Python changes you allowed rebuild). If a build later needs something else here, it stops and says what: start the build again to see the new plan.

This needs the kernel's overlay filesystem (CONFIG_OVERLAY_FS); without it builds don't start. Ready to build for another computer? checks for it.

Accounts and file owners

Packages that need a user or group of their own (messagebus for dbus, polkitd, …) bring an acct-user or acct-group package; installed into the system, it adds the account to the system's own /etc/passwd and /etc/group. The health check makes sure that happened:

  • an account package installed in the system without its account in the system's files is an error;
  • a file an installed package owns, belonging to a user or group number the system has no account for, is an error (it names the account that number belongs to on this computer: the package set the owner while it built, and the system lacks that account);
  • an account with no line in /etc/shadow or /etc/gshadow is a warning.

Before building, an account with a different number here and in the system is warned about: a package that sets file owners by name while it builds gets this computer's number for it.

Where things are

/var/lib/porthole/roots/<name>
The system itself; its Portage settings are in its etc/portage.
/var/cache/porthole/binpkgs/<name>
Its binary packages (its PKGDIR), kept apart from this computer's own; filled when Keeps packages is ticked, kept by Start over, deleted with the system.
/var/cache/distfiles
Downloads: shared with this computer, so a source is only fetched once.
/var/lib/porthole/firstboot/<name>.json
Its first-boot setup (root only: it holds password hashes).
/var/lib/porthole/cross/<name>
The compiler wrappers its builds use, and what you allowed for the rest of its build.
/etc/portage/package.use/porthole-cross-<name>
This computer's USE changes for its build tools, if you allowed any.
<the system>/var/lib/porthole/kernels-to-install
Kernel packages merged into it whose kernel the Install the kernel step hasn't installed yet.
/var/lib/porthole/sandbox/<job>/
What a build tried to write to this computer, when it did.
/var/lib/porthole/health/
The last health report of each system.
/var/lib/porthole/images/<name>/<recipe>/card
The last image made from that recipe: the files to copy to the card.

To copy a finished system somewhere for its computer (an empty folder, or an earlier copy to update), with its repositories and settings made to work there:

porthole-update-service plugin crossdev export <name> <folder>
